# Oracle–PostgreSQL Atomicity Lab

Oracle·PostgreSQL의 **개별 DB 트랜잭션을 관리하고, 실행 중 실패와 커밋 구간에서 데이터가 어떻게 남는지 확인하는 개인 검증 프로젝트**다. 관리자 승인 후 지정 조건·컬럼에 DML을 수행하는 업무를 합성 데이터로 재구성한다.

현재 상태: **설계 검토 단계. 실행 코드·빌드·DB 실험 결과는 아직 없다.**

## 1차 범위

- Oracle용·PG용 DataSourceTransactionManager를 각각 등록하고 트랜잭션 어노테이션으로 관리한다.
- 정상 처리, Oracle 실행 실패, Oracle 실행 후 PG 실패, 양쪽 DML 실행 후 Java 예외를 구분한다.
- 각 사례에서 실행·커밋·롤백 순서와 양쪽 대상 값을 독립된 관찰 연결로 확인한다.
- 한 DB의 커밋 뒤 다른 처리가 실패하는 구간과 처리 도중 조회 결과도 확인한다.
- 실패 이력은 Oracle에 별도 저장하는 구조를 검증하고, 관리자 알림은 Teams 전송 대역으로 확인한다.

여기서 ‘개별 DB 트랜잭션’은 각 DB에 속하는 트랜잭션이라는 뜻이다. 애플리케이션을 PC에서 실행하는지 서버에 배포하는지와 관계가 없다. 저장소 이름의 Atomicity는 검증 주제를 뜻하며, 두 매니저 등록만으로 분산 원자성을 확보했다는 선언이 아니다.

## 기존 실무와의 관계

기존 실무에서는 2026년 상반기 해당 기능을 1인 개발해 운영에 반영했다. Oracle·PG의 각 DataSourceTransactionManager를 사용했고, Java 예외 발생 후 지정 조건·컬럼의 값이 변경되지 않았음을 수기로 확인했다. 실패 이력은 메인 DB인 Oracle에 기록하고 Teams로 관리자에게 알렸다.

이 저장소는 회사 코드의 복사본이나 운영 구조의 완전한 재현이 아니다. 실제 메서드별 매니저 선택·프록시 호출·커밋 완료 순서는 자료로 확인하지 못했으므로, 아래 설계는 검증용 구성으로 명시한다.

## 완료 기준과 추가 요구사항

1차 완료 기준은 [검증 사례 D-01~D-06](docs/verification-plan.md)의 실제 실행과 근거 보존이다. 각 사례의 테스트 판정과 정합성 요구 충족 여부를 따로 기록한다. 부분 커밋을 예상대로 발견한 테스트도 그 자체는 통과할 수 있다.

앞서 확인한 ‘두 독립 DB를 하나의 커밋 결정으로 묶기’와 ‘전체 성공 결정 전 변경값 노출 금지’는 추가 요구사항으로 유지한다. 1차 구성에서 자동으로 충족한다고 가정하지 않는다. 커밋 순서·조회 실험 결과를 확인한 뒤 후속 방식을 결정한다.

XA/JTA·Seata AT·TCC는 후속 비교 후보이며 현재 구현 범위에 포함하지 않는다.
