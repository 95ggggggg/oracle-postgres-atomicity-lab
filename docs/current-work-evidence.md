# 기존 실무 사례에 첨부할 자료

목적: DataSourceTransactionManager를 사용한 실제 업무 흐름과 관찰한 보장을 설명한다. 새 개인 검증 예제와 구분해 작성한다. 경력기술서에는 ‘개별 DB 트랜잭션 관리’로 표현하고, 실행 중 예외의 롤백과 지정 조건·컬럼 대조를 함께 적는다.

후속 확인: Oracle용·PG용 DataSourceTransactionManager를 각각 등록한 점은 사용자 답변으로 확인했다. 이제 필요한 설명은 등록 개수보다 실제 진입 메서드의 매니저 선택·프록시 호출·각 DB의 커밋 완료 순서다. 실행 중 예외에서 롤백된 관찰과 커밋 구간 장애의 보장은 나누어 검토한다.

업무 이유도 확인했다. Oracle·PG가 각각 관리하는 프로모션 연관 데이터가 있어 한 승인 요청의 변경 내용이 양쪽에서 일치해야 했다. Java 예외는 Oracle DML 이전·이후와 PG DML 이후의 세 지점에 주입했다. 특히 PG DML 이후의 예외가 서비스 반환·커밋과 어떤 순서였는지는 실행 자료로 보강한다. 이 답변은 기존 실무에 관한 설명이며 새 저장소의 DB 실험 결과가 아니다.

## 1. 구성 관계표

아래 표는 양식이다. 실제 확인한 값만 채운다. 두 매니저 등록은 사용자 답변으로 확인했다. 아직 확인하지 못한 Bean 이름·메서드 매핑·커밋 순서는 추측해 채우지 않는다.

| 확인 항목 | 첨부할 내용 |
| --- | --- |
| DataSource | Bean 식별자·제품명·JdbcTemplate 또는 DAO 연결 관계 |
| 매니저 | 각 DataSourceTransactionManager 인스턴스가 관리하는 DataSource |
| 진입 메서드 | 어떤 @Transactional 매니저를 선택하는지·프록시 진입 방식 |
| PG 호출 | 같은 메서드의 JdbcTemplate인지, 별도 서비스 Bean의 별도 트랜잭션인지 |
| 오류 처리 | 예외 타입·발생 위치·catch 뒤 전파/rollbackOnly 처리 |
| 완료 순서 | 각 DB의 DML·commit·rollback이 어떤 순서로 발생하는지 |

실제 DataSource Bean과 매니저 생성부, 어노테이션, DML 호출부를 가명 코드 20~40줄로 연결하면 좋다. 접속 URL·비밀번호·회사 원본 테이블명 없이 관계를 보여줄 수 있다.

## 2. 성공·실패 시퀀스

적어도 두 장면을 그린다.

1. 정상: 승인 → Oracle DML → PG 처리 → 각 트랜잭션 완료 → 사용자 결과.
2. 실제 검증: 각 DML의 실행 여부·커밋 여부 → Java 예외를 만든 정확한 위치 → 롤백 → 수기 대조 → 실패 이력·Teams 알림.

로그와 알림의 정확한 호출 순서를 모르면 도식에서 별도 트랜잭션·완료 순서로 확정하지 않는다. ‘양 DB에 전부 롤백’이라는 문장보다 각 DB의 실행·커밋 상태를 표시한 도식이 구체적이다.

## 3. 전후 데이터 표

| 필드 | 채울 내용 |
| --- | --- |
| 요청 식별 | 가명 요청 ID |
| 변경 조건 | 실제 업무 조건을 가명으로 표현 |
| 대상 컬럼 | 실제 비교한 컬럼을 가명으로 표현 |
| 초기 상태 | Oracle·PG 각각의 대상 값 |
| 시도한 변경 | 바꾸려고 한 값 |
| 예외 위치 | 코드상 어느 DML의 전/후인지 |
| 종료 상태 | 각 DB의 commit·rollback·결과 불명 여부 |
| 관찰 결과 | 트랜잭션 종료 후 실제 확인한 두 DB 값 |

전체 컬럼·전체 테이블을 비교했다고 쓰지 않는다. 실제로 검증한 조건과 컬럼만 대상으로 한다. 새 실험의 데이터를 과거 수기 검증의 실제 자료로 소개하지 않는다.

## 4. 실패 이력과 관리자 알림

Oracle 로그 저장 위치는 확인됐다. 제출 자료에서는 이력이 어떤 요청과 연결되는지, Teams에서 관리자가 무엇을 확인할 수 있었는지 가명 예시로 보여준다. 로그가 업무 롤백 후에도 남는 트랜잭션 구조는 확인한 자료가 있을 때 설명한다.

## 5. 선택의 이유와 한계

- 두 DB를 써야 했던 업무 이유.
- 해당 승인 요청이 변경하는 데이터와 허용할 수 없는 불일치.
- DataSourceTransactionManager를 적용한 범위.
- 실제로 확인한 실패와 아직 확인하지 않은 커밋·재기동 장애.
- 새 개인 저장소에서 정상 처리·SQL 오류·Java 예외·커밋 경계·조회로 무엇을 확인할지.

이 다섯 항목이 경력기술서의 ‘고민 과정’을 만든다. 프레임워크 설정 파일만 첨부하면 왜 그 구성을 선택했는지가 남지 않는다.
