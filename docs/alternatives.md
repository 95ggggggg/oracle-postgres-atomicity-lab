# XA/JTA 이외의 접근과 적용 조건

상태: 후속 설계 비교 자료. 1차 범위는 두 DataSourceTransactionManager의 개별 DB 트랜잭션 검증이다. 이 문서의 분산 조정 방식은 아직 선택·구현하지 않았다.

추가로 확인한 요구사항: **전체 성공 결정 전에는 변경값이 다른 업무에 노출되면 안 된다.** 이 조건은 실패 후 최종 값이 일치한다는 조건과 별도로 검증해야 한다.

## 1. 같은 역할을 나누어 본다

| 필요한 역할 | 가능한 접근 | 확인할 차이 |
| --- | --- | --- |
| DB 자원의 커밋 결정을 조정하고 미커밋 변경을 유지 | XA/JTA·지원되는 분산 커밋 코디네이터 | prepare·결정·완료·복구 |
| 비XA 방식으로 DB별 커밋 뒤 전역 취소를 처리 | Seata AT | 전역 결정 전 각 DB의 변경이 커밋됨. 조회·쓰기의 전역 락 연계 필요 |
| 업무 자원을 예약하고 성공 결정 후 확정 | TCC | Try·Confirm·Cancel과 업무 예약·멱등성·복구 설계 필요 |
| 이미 완료된 업무를 보상해 상태 복구 | Saga | 중간 상태 노출·보상 지연·실패·격리 수준을 수용해야 함 |
| 각 DB 트랜잭션을 단순히 순서대로 완료 | DataSourceTransactionManager 두 개 등 | 부분 커밋을 막는 분산 조정 기능은 별도로 필요 |

XA/JTA만이 분산 트랜잭션을 구성하는 유일한 기술은 아니다. 다만 다른 기술을 택할 때도 결정·복구·격리의 책임은 남는다. 독립 DB에 일반 UPDATE를 보내고 Java 예외만으로 이미 커밋한 변경을 원래 트랜잭션에서 롤백할 수는 없다.

## 2. Seata AT — 비XA의 구체적인 후보

공식 지원 목록에는 Oracle·PostgreSQL이 포함된다. AT는 DataSourceProxy, undo_log, 전역 락과 코디네이터를 사용한다. 업무 데이터와 undo log를 같은 개별 DB 트랜잭션에서 커밋한 뒤, 전역 실패 시 undo log를 이용해 보상한다. [지원 DB 목록](https://seata.apache.org/home/feature/), [AT 모드](https://seata.apache.org/docs/user/mode/at/)

개념적인 실행 흐름:

~~~text
전역 트랜잭션 시작
Oracle: 변경과 undo log를 DB별 커밋
PG: 변경과 undo log를 DB별 커밋
전체 성공: 전역 완료·undo 정리·전역 락 해제
중간 실패: 이미 커밋한 변경을 undo log로 복구
~~~

DataSourceTransactionManager를 쓰는 개별 DB의 업무 트랜잭션 경계를 활용할 수 있지만 두 DataSource의 프록시 등록, 전역 XID, 코디네이터와 복구 구성이 추가돼야 한다. 기존 실무에 Seata가 있었다고 확인한 것은 아니다.

### 이번 조건에서의 제약

전역 성공 결정 전에 DB별 커밋이 이뤄지므로 일반 SELECT나 Seata의 제어를 거치지 않는 접근에서 중간 변경을 관찰할 수 있다. 공식 문서는 전역 락과 SELECT FOR UPDATE 등을 이용한 읽기·쓰기 격리 방법을 설명한다. [격리 설명](https://seata.apache.org/docs/user/appendix/isolation/)

따라서 ‘성공 결정 전 노출 금지’를 충족하려면 관련 업무 조회의 접근 경로도 설계에 포함해야 한다. 독립 서비스의 기존 일반 조회를 그대로 두고 AT를 추가한 것만으로 해당 보장을 선언하지 않는다. 경로 밖 쓰기가 undo 대상 값을 바꾼 경우도 검증해야 한다.

지원 DB 목록에 있다는 사실과 모든 SQL을 처리한다는 주장은 다르다. 공식 문서에는 중첩 SQL·복잡한 다중 테이블 SQL·저장 프로시저·트리거 등의 제한이 있다. 실제 사용할 버전과 지정 UPDATE를 검증한다. [SQL 제한](https://seata.apache.org/docs/user/sqlreference/sql-restrictions/)

## 3. TCC — 예약과 확정으로 업무를 재설계

TCC는 Try에서 확인·예약하고, 전역 결정에 따라 Confirm 또는 Cancel을 수행한다. DB 자원 프로토콜 대신 업무 코드가 이 동작을 구현한다. [Seata TCC 문서](https://seata.apache.org/docs/user/mode/tcc/)

이 DML 예제에서 가능한 설계 방향:

~~~text
Try
  Oracle·PG의 실제 status를 바로 바꾸지 않음
  request_id·예정 status·기대 version을 별도 pending 변경으로 보관
  변경 대상을 예약하고 충돌을 제어

전체 성공 결정
  코디네이터가 결정과 복구 상태를 영속화

Confirm
  예약한 변경을 실제 status에 반영
  각 참여자의 완료를 멱등하게 재시도

Cancel
  pending 변경과 예약을 해제
~~~

이 예시는 아직 구현하지 않은 업무 설계다. Try가 실제 상태값을 바꾸지 않고 조회가 실제 상태값만 읽게 하면 성공 결정 전 노출을 피하는 방향으로 만들 수 있다. 그러나 pending 테이블 하나만 추가하는 것으로 완료되는 것은 아니다.

예약을 다른 변경 경로도 지키는지, Confirm이 업무 검증 실패 없이 완료될 조건을 Try에서 확보했는지, 재시도·중복 Confirm/Cancel·늦은 Try·빈 취소를 어떻게 다루는지 정해야 한다. 확인 단계의 영구 오류나 예약을 우회하는 쓰기는 복구를 어렵게 만든다.

일반 SQL 두 개를 그대로 두는 변경보다 구현량이 커진다. 예약·승인·확정이라는 업무 모델이 자연스러운 경우에 검토할 후보이며, 두 DB의 일반적인 물리 트랜잭션·격리와 동일한 보장이라고 표현하지 않는다. 결정 뒤 두 Confirm이 서로 다른 시점에 완료되는 상황도 정의해야 한다.

## 4. Saga — 기존 개별 DB 트랜잭션 매니저와 보상

Oracle 변경 → PG 변경 → 실패 시 Oracle의 보상 변경이라는 흐름을 구성할 수 있다. 요청별 진행 상태·재시도·멱등성과 보상 실패를 영속적으로 관리해야 한다. 보상은 이미 커밋한 업무를 별도 트랜잭션으로 복구하는 처리다. 원래 트랜잭션의 rollback과 다르다. [AWS Saga 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

이 방식은 원래 변경이 먼저 노출될 수 있어 현재의 노출 금지 조건을 그대로 충족하는 대체안으로 채택하지 않는다. 다른 업무가 이후 변경한 값을 예전 값으로 덮어쓰지 않도록 보상 조건도 필요하다.

## 5. 선택 전에 확인할 기준

1. 성공 결정 전 변경값을 기존 일반 조회가 읽을 수 없어야 하는가? 현재 답변은 그렇다.
2. 조회·쓰기 경로를 모두 전역 락 또는 업무 예약 규칙으로 바꿀 수 있는가? 아직 확인하지 않았다.
3. 지정 UPDATE를 예약·확정 업무로 바꾸는 것이 허용되는가? 아직 결정하지 않았다.
4. 새 코디네이터·undo log·pending 변경·복구 운영 중 어느 비용을 감당할 것인가?

기존 일반 DML·조회 경로의 변경을 작게 유지하려면 XA/JTA가 직접적인 후보다. 비XA를 선택하려면 AT의 전역 격리 연계 또는 TCC의 예약·확정 설계를 구체화한 뒤 같은 요구사항으로 검증한다. 현재 XA 제안은 승인·구현된 상태가 아니며, 이 비교를 마친 뒤 구현 방식을 확정한다.

## 6. 대안 선택 시 추가할 검증

| 기준 | AT를 선택하면 확인할 것 | TCC를 선택하면 확인할 것 |
| --- | --- | --- |
| 전역 결정 전 조회 | 일반 조회에서 중간 값 관찰, 연계된 업무 조회에서 차단되는지 비교 | Try 이후 실제 상태 조회가 초기값인지 |
| 실패 복구 | DB별 커밋 뒤 undo, 복구 재시도와 완료 | Cancel과 예약 해제 |
| 동시 쓰기 | 전역 락 참여·우회 쓰기·undo 충돌 | 예약 존중·기대 version·동시 Confirm 충돌 |
| JVM/코디네이터 중단 | 전역 상태·undo log를 이용한 복구 | 결정·예약을 이용한 Confirm/Cancel 재개 |
| 중복 요청 | 같은 XID/요청에 대한 실제 중복 처리 | Try·Confirm·Cancel의 멱등성과 늦은 요청 |

이 표는 추가 검증의 후보이며 실행 결과가 아니다. XA의 prepare·commit 장애 표를 이름만 바꿔 다른 방식의 검증 결과로 재사용하지 않는다.
