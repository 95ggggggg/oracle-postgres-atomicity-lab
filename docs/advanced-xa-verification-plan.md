# 보충 자료: 이전 XA/JTA 검증안

상태: 미확정 후속 후보. 현재 1차 사례는 [D-01~D-06](verification-plan.md)이다. 아래 L/X 사례는 이전 XA 제안의 시험 목록을 보존한 것으로, 현재 1차 완료 기준에 합산하지 않는다. 모두 미실행이다.

# 검증 기준

상태: 모든 사례 `PLANNED`. 아래는 기대 결과이며 아직 관찰한 결과가 아니다.

## 공통 조건

- 실제 Oracle·PG를 사용한다. H2나 Mock만으로 두 제품의 XA 복구를 입증하지 않는다.
- 각 사례는 독립된 합성 요청과 초기 상태를 사용한다.
- 초기 예시: 두 DB의 해당 item은 `status=ACTIVE, version=0`.
- 변경 예시: 동일 요청으로 `status=PAUSED, version=1`.
- DB 관찰은 업무 트랜잭션 바깥의 새 커넥션에서 수행한다.
- 중단 실험에서는 DB와 코디네이터의 영속 저장소를 유지한다.
- 고정 sleep만으로 장애 지점을 추측하지 않고 명시적인 배리어·프로토콜 기록으로 위치를 확인한다.
- 실제 DB 오류, Java 예외, XAResource 경계 주입, 실제 JVM 강제 종료를 서로 다른 증거로 표시한다.
- X-01·X-03에서는 DML 실행 후 전역 결정 전 배리어에서 업무 트랜잭션 바깥의 일반 조회도 수행한다. READ COMMITTED 조건에서 변경 전 값 또는 문서화한 대기 동작을 기대하며, 변경 후 값이 관찰되면 노출 금지 조건을 위반한 것으로 판정한다. 전역 결정 후의 참여자별 완료 시차와 구분한다.

| X-06 | 커밋 결정 후 PG 자원 일시 불가, 이후 복구 | 결과를 롤백 완료로 오인하지 않고 커밋 결정을 이행 | 자원 중단·복원, 재시도/복구 기록, 최종 값·pending 정리 | PLANNED |

L-02는 시스템의 한계를 드러내는 비교 테스트다. 테스트가 예상한 불일치를 확인하면 그 테스트는 성공할 수 있다. 비교 예제의 불일치를 수정된 XA 구성의 통과 결과와 혼동하지 않는다.

X-02에서는 업무 실행 전에 PG에만 변경값 `PAUSED`를 거절하는 테스트용 CHECK 제약을 준비하는 방식 등을 사용한다. 초기값 `ACTIVE`는 유효하고 같은 변경 요청이 Oracle에서는 실행된 뒤 PG에서 실제로 거절되도록 만든다. 제약 준비는 업무 트랜잭션 바깥에서 수행하고, 발생한 DB 오류 코드를 보존한다. 단순히 Java에서 SQLException 객체를 만들어 던진 실행과 구분한다.

## X-05의 완료 판정

강제 종료 전에 반드시 다음 조건을 관찰한다.

1. 두 독립 DB가 실제 XA 자원으로 참여했다.
2. 전역 커밋 결정이 영속화됐음을 코디네이터가 제공하는 근거로 확인했다.
3. 첫 참여자의 커밋이 완료됐다.
4. 다른 참여자는 아직 완료되지 않은 정확한 배리어에 있다.

실제 참여자 순서는 구현체의 자원 정렬에 따라 확인한다. Oracle이 항상 먼저라는 가정으로 테스트를 작성하지 않는다. 결정 영속화 위치를 확인할 수 없다면 해당 실행을 ‘정확한 커밋 경계에서의 재기동 검증’으로 승격하지 않는다.

재기동 때 같은 코디네이터 로그를 사용하고, 복구가 완료될 때까지 상한이 있는 조건 대기로 관찰한다. 제한 시간은 실패를 검출하기 위한 실험 조건이지 운영 SLA가 아니다.

최종 값뿐 아니라 pending/prepared 자원의 정리와 복구 오류도 확인한다. 최종 값만 같고 복구가 계속 실패하는 실행을 완전 통과로 기록하지 않는다.

## 준비된 트랜잭션 관찰

PG에서는 `pg_prepared_xacts`와 prepared transaction 설정을 확인한다. Oracle은 해당 버전의 XA·미결 트랜잭션 관찰 수단과 복구 권한을 공식 문서에 맞춰 구성한다. 애플리케이션 계정에 임의로 광범위한 관리자 권한을 부여하는 방식으로 숨기지 않는다. [PostgreSQL 문서](https://www.postgresql.org/docs/current/sql-prepare-transaction.html), [Oracle 분산 트랜잭션 문서](https://docs.oracle.com/en/database/oracle/oracle-database/26/jjdbc/distributed-transactions.html)

## 로그·알림 보조 검증

업무 롤백 뒤 Oracle 실패 이력을 별도 처리하는 새 설계를 구현하면 해당 저장 경계도 테스트한다. 업무 데이터 미변경과 로그 저장을 별도 assertion으로 둔다. Teams는 실제 전송 대신 기록용 대역으로 확인한다. Oracle 자체가 불가한 사례에서 Oracle 로그 저장이 실패하는 결과도 숨기지 않는다.
