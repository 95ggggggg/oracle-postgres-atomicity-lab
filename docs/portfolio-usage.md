# 경력기술서에서 설명하는 방법

## 기존 운영 경험

사용자 답변으로 확인한 내용은 다음과 같다.

- 2026년 상반기 관리자 승인 후 Oracle·PG DML 처리를 1인 구현.
- 각 DataSourceTransactionManager와 트랜잭션 어노테이션으로 개별 DB 트랜잭션 관리.
- Java 예외로 실패 경로를 검증하고 지정 조건·컬럼의 값을 수기로 대조.
- Oracle 실패 이력·Teams 관리자 알림, 운영 반영 후 현업 사용.

경력기술서에는 다음처럼 적는다.

> Oracle·PostgreSQL의 개별 DB 트랜잭션을 관리하고 관리자 승인 후 지정 조건·컬럼에 DML을 수행하는 기능을 1인 개발했습니다. Java 코드에서 예외를 발생시킨 뒤 양 DB의 대상 값을 수기로 대조해 데이터가 변경되지 않는 것을 확인했습니다. 실패 이력은 Oracle에 기록하고 Teams로 관리자에게 알렸으며, 운영에 반영되어 현업에서 사용 중입니다.

‘정합성을 적용했다’만 적는 것보다 어떤 처리에서 무엇을 확인했는지 쓰는 편이 담당 범위와 근거를 보여준다. 이 문장은 실행 중 예외의 검증을 설명하며, 두 DB의 모든 장애에 대한 원자적 커밋까지 주장하지 않는다.

매니저별 메서드 적용·프록시 호출·커밋 순서와 로그 저장 트랜잭션은 아직 소스로 확인하지 못했다. [실무 첨부 자료](current-work-evidence.md)로 설명을 보강한다.

## 새 개인 검증

현재는 설계 단계다. 새 저장소를 소개할 때는 다음처럼 쓴다.

> 운영에서 다룬 Oracle·PostgreSQL 변경 처리를 합성 데이터로 재구성하는 검증 프로젝트를 설계했습니다. 두 DataSourceTransactionManager의 실행 중 실패·커밋 순서·처리 중 조회를 확인하는 사례를 정리했으며, 실행 결과는 구현 후 보완할 예정입니다.

D-01~D-06을 실제 완료하면 아래 틀을 관찰한 결과로 채운다. 아직은 제출용 성과 문장이 아니다.

> 두 DB의 개별 트랜잭션을 구성하고 정상 처리·실제 SQL 오류·Java 예외의 결과를 독립 연결에서 확인했습니다. [실행 기록 링크]에서 [실제 관찰한 롤백 결과]를 검증했고, [커밋 경계와 조회에서 확인한 한계]를 기록했습니다.

결과가 나기 전에 ‘양쪽 원자성 확보’, ‘모든 실패 시 전체 롤백’, ‘XA를 대체’라고 쓰지 않는다. 후속 분산 조정 방식을 구현하면 그때 사용한 구성과 검증 결과를 추가한다.

## 같은 문서 안의 위치

기존 DML 사례의 마지막에 ‘후속 개인 검증’으로 연결한다. 기존 운영 구현과 새 검증의 수행 시기·소스·실행 증거를 구분한다. 주요 프로젝트 수는 지원 공고의 제한에 맞춘다.

읽는 사람이 확인할 링크는 README, 매니저·메서드 설계, D-01~D-06 실행 결과다. 테스트 개수보다 예외 위치·커밋 여부·최종 값이 이어지는 사례를 먼저 보여준다.
