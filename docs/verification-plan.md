# 검증 기준

상태: 모든 사례 `PLANNED`. 아래 내용은 기대 결과이며 실측 결과가 아니다.

## 공통 조건

- 실제 Oracle·PostgreSQL과 각 DataSourceTransactionManager를 사용한다.
- 테스트 입력은 합성 item의 지정 조건·컬럼으로 한정한다.
- 초기값은 양쪽 `status=ACTIVE, version=0`, 변경값은 `status=PAUSED, version=1`로 둔다.
- 스키마·제약 준비는 업무 트랜잭션 전에 수행한다.
- 업무 종료 후 값은 각 DB의 새 관찰 연결로 확인한다.
- 매니저·커넥션별 DML 시작/완료, commit 시작/완료, rollback, 예외 발생·전파를 추적한다.
- 테스트 바깥에서 모든 업무 변경을 자동 롤백하는 구성을 사용하지 않는다.
- 격리 수준·버전·타임아웃과 failpoint 위치를 기록한다.
- 커밋·조회 시점은 배리어로 통제한다. sleep만으로 시점을 추정하지 않는다.
- Java 예외, 실제 SQL 오류, 프로세스 중단을 서로 다른 검증으로 표시한다.

## 1차 사례

| ID | 조건·실패 위치 | 확인할 결과 | 핵심 증거 | 상태 |
| --- | --- | --- | --- | --- |
| D-01 | 정상 요청 | 양쪽 PAUSED·1, 각 DB 커밋 완료 | 실제 DML·커밋 순서, 독립 연결의 최종 값 | PLANNED |
| D-02 | Oracle DML 실행 오류 | Oracle 롤백, PG 실행 0회, 양쪽 ACTIVE·0 | Oracle 오류 코드, PG 호출 횟수, 최종 값 | PLANNED |
| D-03 | Oracle DML 완료 후 실제 PG SQL 오류 | PG·Oracle 미커밋 변경 롤백, 양쪽 ACTIVE·0 | PG 오류 코드, 양쪽 종료 기록, 최종 값 | PLANNED |
| D-04 | 양쪽 DML 후 PG 메서드 반환 전 Java 예외 | 예외 전파로 양쪽 롤백, ACTIVE·0 | 양쪽 SQL 실행 완료, 예외 위치, 롤백 기록, 최종 값 | PLANNED |
| D-05 | PG 커밋 완료 후 Oracle 서비스에서 Java 예외 | Oracle ACTIVE·0, PG PAUSED·1의 부분 커밋 | PG 커밋 완료 → 예외 → Oracle 롤백 순서, 최종 값 | PLANNED |
| D-06 | 커밋 전과 첫 DB 커밋 후에 별도 연결로 조회 | 커밋 전 값과 첫 커밋 뒤 노출 차이를 관찰 | 조회 배리어·격리 수준·DB별 값·요청 완료 시점 | PLANNED |

D-05의 순서는 [검증용 서비스 배치](design.md)를 전제로 한다. 회사 운영 구조에 같은 문제가 있었다는 판정이 아니다. 실제 코드가 다른 완료 순서를 만든다면 failpoint와 기대값을 그 구조에 맞춰 고친다.

## 실제 SQL 오류를 만드는 방법

D-02는 Oracle에만 변경값 PAUSED를 거부하는 테스트 CHECK 제약을 미리 준비한다. 초기값 ACTIVE는 유효하게 유지한다. Oracle이 거절한 뒤 PG를 호출하지 않았는지 확인한다.

D-03은 같은 제약을 PG에만 준비한다. Oracle에서는 동일 변경이 실행되고 PG의 UPDATE가 실제로 거절되게 한다. 제약 준비는 업무 트랜잭션 바깥에서 완료한다. 발생한 제품별 SQL 오류 코드와 실제 실행 SQL을 보존한다.

Java에서 SQLException 객체를 만들어 던진 실행은 실제 DB 오류로 집계하지 않는다. 두 경우를 별도 검증으로 남긴다.

## Java 예외와 커밋 경계

D-04의 예외는 PG 메서드 본문에서 DML을 수행한 뒤, PG 프록시가 커밋하기 전에 발생시킨다. PG 서비스 호출이 정상 반환한 뒤의 예외와 혼동하지 않는다.

D-05는 PG 서비스 프록시가 정상 반환하고 PG 커밋 완료까지 관찰한 후 Oracle 메서드에서 예외를 발생시킨다. 두 DB의 최종 값이 다르면 이를 부분 커밋으로 기록한다. 이미 커밋한 PG를 원래 트랜잭션에서 롤백했다고 기록하지 않는다.

이번 1차 범위의 D-05는 결정적인 Java 예외 주입이다. 네트워크 단절·DB 서버 종료·JVM 강제 종료를 검증한 것으로 확대하지 않는다.

## 처리 중 조회

D-06은 READ COMMITTED인 독립 관찰 연결로 다음을 확인한다.

1. 양쪽 DML 후 어느 쪽도 커밋하기 전의 값.
2. PG 커밋 완료 후 Oracle 완료 전의 값.
3. 전체 요청이 종료된 뒤의 값.

각 조회 시점에 업무 진행을 배리어로 멈추고 실제 관찰값·대기·시간 초과를 남긴다. 검증용 배치에서는 두 번째 시점에 PG의 변경값과 Oracle의 이전 값이 관찰되는지 확인한다.

단일 전역 커밋 결정을 구현하지 않은 상태에서는 ‘전체 성공 결정 전 노출 금지’를 충족했다고 표시하지 않는다. 커밋 전 비노출과 요청 완료 전 노출은 별개로 기록한다.

## 테스트 판정과 요구사항 판정

| 기록 | 뜻 |
| --- | --- |
| 테스트 판정 | 지정 위치에서 실행됐고 예상한 현상을 관찰했는가 |
| 대상 데이터 정합성 | 해당 실패 후 양쪽 변경이 모두 반영 또는 모두 미반영인가 |
| 단일 커밋 결정 | 두 DB의 완료를 하나의 결정으로 조정했는가 |
| 결정 전 노출 금지 | 성공 결정 시점을 식별하고 그 전 비노출을 검증했는가 |

부분 커밋을 발견하는 D-05는 테스트 자체가 통과해도 양쪽 미변경 요구는 충족하지 못한다. 실행 전이나 근거 부족 항목은 미검증으로 둔다.

## 이력·알림 보조 검증

D-04를 기준으로 업무 값 미변경, 별도 Oracle 실패 이력 1건, 관리자 알림 대역 기록을 각각 확인한다. D-05에서는 부분 반영 사실이 이력에 드러나는지 확인한다. 모든 실패를 ‘전체 롤백 성공’으로 기록하지 않는다.

Oracle 이력 저장 자체가 실패하는 경로는 관찰 결과를 남긴다. 실제 Teams 전송 성공이나 외부 알림의 원자성으로 설명하지 않는다.

## 후속 범위

동일 요청 재시도, 동시 변경, 프로세스·DB 중단과 재기동, 분산 커밋·복구는 1차 결과 확인 후 별도 설계한다. 기존 XA 시험안은 [보충 검증 기준](advanced-xa-verification-plan.md)에 남긴다. 아직 실행하지 않은 사례는 완료 수에 포함하지 않는다.
